1. 项目定位

项目名称： LoreGuard
项目类型： 带角色知识边界、披露条件和对话上下文的 RAG 系统。
目标： 完成一个能够演示、评估和复现的 AI 工程作品，用于求职简历。

游戏是应用场景，核心技术包括数据建模、权限过滤、语义检索、上下文管理、生成约束和评估。

2. 场景设定：Moonlight Village

玩家是月光村的一名村民。村长 Aldren 与魔鬼交易，准备献祭村民，封锁村庄以防止他们逃离，并以“村外出现致命疫病”为借口。

两名初始 NPC：

角色	知识与信念	披露规则
Rowan：守卫	相信村长的疫病公告，不知道献祭计划	可以谈论自己知道的信息
Mira：草药师	读过契约和封锁命令，知道部分真相	完成 earn_miras_trust 后才透露秘密

核心区别：世界真相、角色相信什么、角色允许透露什么，是不同的概念。

3. 已完成的开发过程
阶段 1：定义需求与验收场景 ✅

编写英文 scenarios.md，明确世界设定、角色知识、玩家状态和五个基础场景：

Rowan 按照疫病说法解释封村。
Mira 在信任前拒绝透露内幕。
Mira 在信任后透露契约与献祭计划。
玩家取得 Mira 信任，不会让 Rowan 自动获得新知识。
未设定的信息，如魔鬼真名，不能被编造。

学到的原则： 先定义允许与禁止的行为，再实现系统。

阶段 2：结构化知识与权限过滤 ✅

建立 data/world.json：

facts：命题文本与作者视角的真假。
characters：角色身份、语气和知识列表。
source：角色获取信息的来源。
stance：角色对信息的态度。
disclose_after：信息披露条件。
player_states：任务完成情况。

编写 inspect_world.py，实现：

load_world()
inspect_knowledge(world, npc_id, state_id)

把角色知识分成 disclosable 和 withheld。

学到的原则： “不知道”和“知道但不能说”需要分别表达；作者视角的真假不能直接暴露给 NPC。

阶段 3：关键词检索基线 ✅

编写 retrieval.py：

先进行权限过滤。
用正则表达式提取英文单词。
计算问题和资料的单词集合交集。
按重合词数量排序，取前 top_k 条。

发现的问题： 同义表达可能匹配不到，常见词也可能造成误匹配。

阶段 4：Embedding 语义检索 ✅

编写 semantic_retrieval.py，使用：

sentence-transformers/all-MiniLM-L6-v2

将问题和资料编码为 384 维向量，归一化后用点积计算余弦相似度。

理解的关键点：

比较的是问题与事实的 text，不是 fact_id。
相似度不是正确概率。
排名靠前不代表资料足以回答问题。
当前语义检索没有 score 阈值。

观察到的问题： Can I depart? 与封门事实的匹配分数较低，暴露了短问题缺少上下文、资料描述不完整等问题。

阶段 5：预计算与复用资料向量 ✅

编写 indexed_retrieval.py：

build_index(world, model)
retrieve(world, model, index, npc_id, state_id, query, top_k)

启动时建立：

fact_id → embedding

每次查询只编码问题，并取出允许披露的候选向量进行比较。

当前限制： 索引保存在内存中；程序重启后重建，文本或模型变化后也需要重建。

阶段 6：组装生成上下文 ✅

编写 generation.py 中的 build_messages()，组合：

NPC 身份与语言风格。
事实使用和披露规则。
检索证据 evidence。
玩家问题。

为信任前的 Mira 添加不含秘密内容的保密行为指令。

学到的原则： evidence 是检索得到的回答依据，不一定是客观真相；Rowan 可以依据自己相信的错误公告回答。

阶段 7：接入 Gemini API ✅

使用 google-genai SDK，建立 generate_dialogue() 与 chat.py。

跑通：

玩家输入 → 检索 → 组装上下文 → Gemini 生成台词

API Key 通过环境变量读取。

初步测试： 暂未观察到基础场景中的保密问题，但尚不能据此认定系统可靠。

阶段 8：改善台词自然度 ✅

发现 NPC 反复复述：

Aldren sealed the gates three days ago.

调整提示与角色风格：

证据是事实边界，不是必须朗读的脚本。
优先回答当前问题。
不主动重复无关日期和背景。
允许表达关心、犹豫等态度，但不能创造事实。

学到的原则： 回答依据充分与语言自然度，需要分别检查。

阶段 9：接入短期对话历史 ✅

实际补上并检查 history：

保存最近三轮完整问答。
构建输入时加入旧问题与旧回答。
Gemini 使用 user / model 表示对话角色。
生成成功后更新历史。

当前限制： 历史只在内存中；会话使用固定 NPC，切换角色或重测状态时需要清空历史。

阶段 10：结合历史改写检索问题 ✅

亲手实现并调试 rewrite_dialogue(client, query, history)：

没有历史时直接返回原问题。
根据历史补全代词与省略内容。
保留原意，不回答问题。
不将猜测变成事实。
指代不清时返回原问题。

例如：

Have you seen it yourself?
↓
Has Rowan personally seen the sickness outside the village?

数据流：

改写问题 → embedding → 检索 evidence
原问题 + history + evidence → 生成台词

已修正变量重名、历史顺序描述和响应文本读取等问题。

阶段 11：扩充资料与初步观察 ✅

新增五条 Rowan 的普通知识：

值班时间。
水井位置。
食物配给。
Mira 诊所。
村庄集市。

按提供的版本，知识库共有 9 条事实，Rowan 有 7 条可披露知识；测试时使用 top_k=2。

观察到模型能组合集市和诊所信息回答，但也发现：

“Mira 配制药草”并不能证明“她出售烹饪香草”。

学到的原则： 相关资料不一定能支持模型进一步推断出的结论。

4. 当前系统状态
加载世界数据并预计算向量
        ↓
接收玩家问题
        ↓
根据历史改写检索问题
        ↓
按角色与任务状态过滤知识
        ↓
语义检索 Top-K 证据
        ↓
原问题 + 历史 + 证据 + 角色规则
        ↓
Gemini 生成回答
        ↓
更新短期历史

当前已跑通主流程，主要依靠手动测试。

尚未完成：动态任务状态、角色历史隔离、存档、系统化评估、界面和作品集包装。

7. 简历叙事

LoreGuard 是一个以游戏 NPC 为验证场景的上下文感知 RAG 项目。我实现了角色知识与披露条件过滤、语义检索、短期历史和查询改写，并通过实际对话检查检索与生成失败。后续将完善动态状态和对照评估，验证系统的信息边界与回答质量。

只有实际完成并测量过的功能与结果，才作为简历中的已完成成果。
